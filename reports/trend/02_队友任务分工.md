## 2. 组员 1：时序趋势预测（PatchTST 建模）

### 2.1 输入数据

| 文件 | 路径 | 说明 |
|:----|:----|:-----|
| **`patchtst_role_month_features.json`** | `data/gold/patchtst_role_month_features.json` | **核心输入**：69 角色 × 77 月面板数据，已包含 time_idx |
| **`role_taxonomy.json`** | `data/gold/role_taxonomy.json` | 角色定义：role_id → canonical_role 映射 |
| `role_month_features.json` | `data/gold/role_month_features.json` | 原始合并特征（备选，如果需自定义面板构建） |

### 2.2 核心任务

#### 任务 1.1：实现 PatchTST 模型训练

使用 `patchtst_role_month_features.json` 训练 PatchTST 时序预测模型。

**目标**：预测 **2026 年 6 月以后**（当前数据截止到 2026 年 5 月）每个角色的趋势。

**数据说明**：

| 列名 | 说明 | 是否预测目标 |
|:----|:----|:-----------|
| `jd_demand_index` | JD 需求指数 | ✅ **主要预测目标** |
| `gdelt_sentiment_index` | GDELT 新闻情绪 | ❌ 输入特征 |
| `gdelt_article_count` | GDELT 文章数 | ❌ 输入特征 |
| `gdelt_event_impact_score` | 重大事件冲击 | ❌ 输入特征 |
| `github_repo_count` | GitHub 仓库数 | ❌ 输入特征 |
| `arxiv_paper_count` | arXiv 论文数 | ❌ 输入特征 |
| `time_idx` | 时间索引（每角色从 0 开始） | ❌ 辅助列 |

**建议方法（可自由选择）**：
- 使用 **PatchTST** 作为主要模型（输入输出都是多变量时序）
- 或使用 Transformer / LSTM / XGBoost 等替代方案
- 多任务学习：同时预测所有 69 个角色，利用角色间相关性

#### 任务 1.2：将 GDELT 和技术热度作为外生变量加入

JD 数据是主要信号，但 GDELT 新闻情绪和技术热度可作为辅助特征增强预测。

**几种可行的融合方式**（选一种即可）：
- **方式 A**（通道合并）：将 GDELT/TechHeat 特征作为额外通道，与 JD 一起输入 PatchTST
- **方式 B**（两阶段）：先用 JD 预测基础趋势，再用 GDELT/TechHeat 做残差修正
- **方式 C**（注意力加权）：在模型中加入特征级注意力，让模型自动学习各源的权重

#### 任务 1.3：实现证据回溯接口

**这是关键需求**：得到预测结果的同时，必须能够回溯过去的数据指标变化，便于 Agent 生成证据说明。

**具体来说**，对于每个角色的预测结果，需要能回答以下问题：
- "为什么你认为这个角色会上升/下降？"
  → 回溯过去 N 个月的 `jd_demand_index` 趋势
  → 回溯过去 N 个月的 `gdelt_sentiment_index` 变化
  → 回溯过去 N 个月的 `github_repo_count` 变化
- "过去有什么明显的事件/转折点？"
  → 找出指标突变的月份

**建议实现方式**：
- 保存模型在测试集上的**注意力权重**或**特征重要性**
- 提供一个 `get_evidence(role, month) → dict` 接口，返回该角色该月的历史指标序列 + 模型对该月的归因分析
- 输出格式示例：
```python
{
  "canonical_role": "AI Engineer",
  "prediction_month": "2026-07",
  "predicted_demand_index": 0.72,
  "trend_direction": "up",
  "historical_trend": {
    "months": ["2025-07", "2025-08", ..., "2026-06"],
    "jd_demand_index": [0.45, 0.48, ..., 0.65],
    "gdelt_sentiment_index": [0.3, 0.35, ..., 0.55],
    "github_repo_count": [120, 135, ..., 180]
  },
  "key_factors": ["JD 需求持续上升", "GDELT 新闻情绪改善", "GitHub 活跃度增长"]
}
```

### 2.3 交付物

| 交付物 | 说明 |
|:------|:-----|
| 训练好的 PatchTST 模型 | 模型权重文件（<100MB，可放 Git）/ 或训练脚本 |

### 2.4 自由发挥空间

- 模型架构（PatchTST / Transformer / LSTM / XGBoost 均可）
- 特征融合方式（通道合并 / 两阶段修正 / 注意力加权）
- 预测步长（3 个月 / 6 个月 / 12 个月）
- 回测评估方法（滚动验证 / 时间序列交叉验证）

### 3.2 核心任务

#### 任务 2.1：理解证据数据

先熟悉 GDELT 事件数据的结构：

```
gdelt_gkg_role_documents.jsonl (每行一条事件)
  ├── canonical_role    → 匹配到的岗位角色名
  ├── month             → 事件发生月份
  ├── url               → 新闻原文链接
  ├── source_domain     → 新闻来源域名
  ├── themes            → GDELT 主题标签
  ├── tone              → 情绪分数（逗号分隔的 6 个数值）
  ├── bucket_name       → 所属主题桶（ai_llm / security / ...）
  ├── match_weight      → 角色匹配权重
  ├── matched_terms     → 匹配到的关键词
  └── matched_term_count → 关键词匹配数
```

`tone` 字段说明：`"tone,positive,negative,polarity,activity,self_reference"`，第一个值是综合情绪分（-100~100，正=正面，负=负面）。

#### 任务 2.2：构建证据索引

你需要构建一个**证据检索系统**，当组员 3（Agent）给出一个角色名和时间范围时，能快速找到相关的事件证据。

**建议方案（自由发挥）**：

**方案 A - 向量数据库**（推荐）：
- 使用 ChromaDB / FAISS / Qdrant 等
- 将每条事件作为文档存储
- 每个文档包含：title（从 URL 可抓取）、情绪分、来源、匹配角色
- 需要时通过角色名 + 语义搜索检索

**方案 B - 倒排索引**：
- 对 canonical_role 和 themes 建立倒排索引
- 用 ElasticSearch / Whoosh / 简单的字典索引
- 按角色 + 时间范围过滤

**方案 C - 简单的文件分区**：
- 按角色将事件拆分到不同文件
- 按月份分片
- 查询时直接读对应角色的文件

#### 任务 2.3：与组员 1 的预测结果联动

核心流程：

```
组员 1 的预测结果
    │
    ▼
找到"趋势上升/下降"的角色
    │
    ▼
在事件证据中搜索该角色的相关事件
    │

按时间排序，筛选高权重事件
    │
    ▼

```

```python
    """
    返回指定角色在时间范围内最相关的 N 条事件证据。
    每条证据包含：url, source_domain, tone, themes, match_weight
    """
    pass
```

#### 任务 2.4：补充 JD 证据

除了 GDELT 事件，`processed_jd_jobs.json` 中包含真实的 JD 岗位链接。可以作为"岗位确实存在"的证据补充。

## 4. 组员 3：Agent 集成与全链路跑通

### 4.1 职责概述

你是**整个项目最终的"收口人"**，负责将所有模块集成到一个统一的 Agent 系统中。你的工作不只是对接趋势预测和证据链，而是打通从**用户输入简历 → 完整分析 → 可视化展示**的端到端链路。

**你需要集成的模块：**

```
┌──── 用户输入 ─────────────────────────────────────────┐
│  方式 A: 直接粘贴简历文本                               │
│  方式 B: 自然语言对话（"我想转行到 AI 方向"）             │
│  方式 C: 已有用户直接查询趋势                             │
└────────────────────────────────────────────────────────┘
                            │
┌─── Agent 内部流程 ────────▼────────────────────────────┐
│                                                        │
│  步骤 1: ExtractorService.extract(resume)              │
│          → 用户画像: 技能/经验/目标角色                  │
│                                                        │
│  步骤 2: CareerPathwayService.plan(profile)            │
│          → 技能差距分析 + 学习路径                      │
│                                                        │
│  步骤 3: RecommenderService.recommend(profile)         │
│          → 当前匹配岗位推荐                             │
│                                                        │
│  步骤 4: TrendService (你两位队友的产出)                │
│          → 目标角色的趋势预测 + 证据                    │

└────────────────────────────────────────────────────────┘
                            │
┌─── 输出 ──────────────────▼────────────────────────────┐
```

#### 任务 3.3：设计 Agent 交互场景

Agent 需要覆盖以下用户场景（按复杂度排序）：

**场景 1：趋势查询**（最简单的切入）
```
用户: "AI Engineer 未来趋势怎么样？"
Agent: → 调趋势接口 → 调证据接口 → 生成回答
```

**场景 2：简历分析 + 趋势**
```
用户: [粘贴简历]
Agent: → 调 Extractor → 分析技能/经验 → 识别目标角色
       → 调趋势接口 → 给出该角色的趋势预测
       → 综合回答: "你的技能适合转 AI Engineer，该角色正在上升"
```

**场景 3：完整职业规划**
```
用户: "我有 2 年 Python 经验，想转 AI 方向"
Agent: → 调 Extractor（即使不是完整简历也可分析）
       → 调 CareerPathway → 技能差距分析
       → 调 Recommender → 当前可投岗位
       → 调趋势接口 → 目标角色趋势
       → 综合回答: 路径+学习资源+岗位推荐+趋势+证据
```

**场景 4：多角色对比**
```
用户: "帮我对比一下前端和后端的发展前景"
Agent: → 调趋势接口（多个角色）
       → 调证据接口
       → 生成对比分析
```

## 5. 组间协作建议

### 5.1 接口约定

三个组员之间的接口建议尽早对齐：

```
组员 1 → 组员 3: predict(role, months) → {trend, confidence, history, factors}
组员 2 → 组员 3: retrieve_evidence(role, time_range) → [event1, event2, ...]
```

### 5.2 开发顺序建议

```
第 1 周: 组员 1 训练基础模型 + 组员 2 建立证据索引
第 2 周: 组员 1 完成证据回溯接口 + 组员 2 完成检索接口
第 3 周: 组员 3 集成两端 + 跑通链路
第 4 周: 联调 + 可视化 + 文档
```

### 5.3 沟通建议

- 组员 1 和组员 2 的接口定义最好**一起协商**，确保组员 3 拿到的结果格式一致
- 组员 3 可以先 mock 预测和证据接口，不等待组员 1 和 2 完成再开始
- 每周至少一次 sync，确保接口对齐
