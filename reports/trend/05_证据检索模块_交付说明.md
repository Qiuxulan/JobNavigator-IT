# 证据检索（RAG）+ 事件入图 模块交付说明

> 负责人：组员 2（证据链 RAG）。本文说明：做了什么、怎么做、用了什么、代码设计逻辑、每个文件交付什么、怎么用。

---

## 1. 这个模块是干什么的

把 B 的趋势预测（某岗位未来涨/跌）**解释清楚并给出可追溯证据**：

- 输入：B 的趋势结论（岗位 + 月份 + 方向）、A 的 GDELT 事件（172 万条）、JD 岗位数据（7 万条）。
- 输出：① 每条结论的证据（聚合信号 + 代表性事件 + JD）；② 事件接入知识图谱（`AFFECTS` 边）。
- 用处：Agent 回答"为什么这个岗位会涨"时有据可依；前端角色页展示证据卡片；图谱上岗位旁挂事件。

---

## 2. 核心设计逻辑（5 个关键决策）

1. **一次选择，多处产出**：检索核心只有一份（`EvidenceService`），运行时接口、批量证据文件、图谱事件边**共用同一份选择结果**，绝不重复实现检索。

2. **两层证据**（应对数据噪音的关键）：
   - **主力 = 聚合信号**：一个岗位某月相关新闻的篇数/情绪/机会·风险占比/净信号。多篇噪音文档的统计量稳健，覆盖率高（97.9%）。
   - **佐证 = 干净样本事件**：过严格约束才入选的少量事件，标注"相关性近似"。

3. **四重约束相关性闸门**（GDELT 无正文，只能用约束换精度）：
   ① 技能词白名单（`skill_vocab.json` 662 别名）② 科技∧经济主题共现 ③ 垃圾域名黑名单 ④ 硬丢 URL 伪词（html/.net 占噪音约 88%）。

4. **方向归因排序**：复合分 `0.4·主题相关(BM25) + 0.3·方向对齐 + 0.2·事件重要性 + 0.1·时间近度`。方向对齐为软加权（涨偏好正面事件、跌偏好负面），保留少量反向事件支撑风险提示。

5. **零依赖**：索引用纯标准库按"岗位+月份"分片（方案C），不依赖 duckdb/ES/向量库，团队无需额外安装。

## 3. 数据流

```
A: gdelt_gkg_role_documents.jsonl(2.6GB) ┐
   processed_jd_jobs.json(170MB)         │
B: role_trend_scores.json(方向/月份/岗位) │
   role_taxonomy.json(role_id 映射)      │
        │                                │
        ▼ ① build_evidence_index.py      │
   data/processed/evidence_index/        │  按 岗位/月份 分片
        │                                │
        ▼ ② EvidenceService.retrieve_evidence(role, months, top_k, direction)
        │   过四重约束 → 方向归因排序 → 聚合 + TopK事件 + JD
        ├─③ TrendService / GET /trends, GET /evidence   → 组员3、前端
        ├─③ build_trend_evidence.py → trend_evidence_v1.jsonl + 评估报告 → D
        └─④ build_event_graph.py    → event 节点 + AFFECTS 边 → 知识图谱
```

## 4. 用了什么

| 用途 | 选型 | 理由 |
|---|---|---|
| 索引/过滤 | 纯标准库分片（岗位/月份 jsonl） | 2.6GB 不进内存、零依赖、按岗位+月份秒级定位 |
| 关键词检索 | 纯 Python BM25（Okapi） | 零依赖、可移植 |
| 相关性约束 | `skill_vocab.json` 白名单 + GDELT themes + 域名黑名单 | 无正文下用约束换精度 |
| 复用资产 | `role_taxonomy`(role_id)、队友 `build_career_graph_v2`/`export_graph_interactive_v2` | 图谱节点天然对齐、复用渲染器 |
| 可视化 | vis-network（CDN，数据内联 HTML） | 双击即开，无需起服务 |
| 不用 | ElasticSearch / 向量库 | 查询是结构化过滤+排序，非全文搜索，部署成本不划算 |

## 5. 代码清单（每个文件：做什么 / 怎么做 / 产出 / 怎么用）

### ① `pipelines/trend/build_evidence_index.py` — 离线索引层
- **做什么**：把全量 GDELT + JD 转成可快速过滤的分片。
- **怎么做**：流式读 jsonl（2.6GB 不进内存），按 `events/<岗位>/<月份>.jsonl`、`jobs/<岗位>.jsonl` 写出；tone 解析、字段瘦身。
- **产出**：`data/processed/evidence_index/`（含 manifest.json）。
- **怎么用**：`python pipelines/trend/build_evidence_index.py`（全量约 2 分钟）/ `--sample`（样本）。

### ② `app/services/evidence.py` — 检索核心 + 运行时接口
- **做什么**：证据检索（任务分工 §3 的 `retrieve_evidence`）。
- **怎么做**：读分片 → 四重约束闸门 → 方向归因复合排序 → 混 JD → 去重 TopK；并算聚合信号。`rerank()` 留作语义升级钩子。
- **产出**：`retrieve_evidence(role, months, top_k, direction) -> {aggregate, events, jobs, ...}`。
- **怎么用**：`from app.services.evidence import EvidenceService`。

### ③ `app/services/trend.py` — 服务接入
- **做什么**：`TrendService.get_signal` 返回趋势信号时**自动带证据**。
- **怎么做**：算出方向后调 `EvidenceService`，映射成 `TrendEvidence` 填入 `TrendSignal.evidence`；索引缺失时返回空不报错。
- **怎么用**：`TrendService.get_signal("AI Engineer")` → `.evidence`。

### ③ `app/api/routes.py` — REST 接口
- `GET /v1/trends/{job_role}`：趋势**带证据**。
- `GET /v1/evidence/{job_role}?start_month&end_month&top_k&direction`：纯证据（aggregate + events + jobs），支持别名解析。

### ③ `pipelines/trend/build_trend_evidence.py` — 批量证据文件 + 评估
- **做什么**：对 B 的 340 条结论批量出证据文件 + 评估报告。
- **怎么做**：逐条调 `EvidenceService`，按契约 §5 写 jsonl（含 aggregate/evidence_topk/jd_evidence/risk_notes）。
- **产出**：`data/gold/trend_evidence_v1.jsonl`、`reports/trend_explanation_eval_v1.md`。
- **怎么用**：`python -m pipelines.trend.build_trend_evidence`（约 80 秒）。

### ④ `pipelines/graph/build_event_graph.py` — 事件入图
- **做什么**：把检索选出的代表性事件接到知识图谱。
- **怎么做**：复用同一检索选择 → event 节点（按 url 去重）+ `AFFECTS(event→job)` 边（`dst_id`=role_id，和队友 job 节点对齐）→ 复合分 P60 阈值过滤。
- **产出**：`data/processed/event_graph_v1.json`；`--write-db` 写 Postgres `graph_nodes`/`graph_edges`。
- **怎么用**：`python -m pipelines.graph.build_event_graph [--write-db]`。

### ④ `pipelines/graph/build_event_graph_view.py` / `build_unified_graph_view.py` — 可视化
- **做什么**：渲染交互式图谱 HTML。
- `build_event_graph_view.py`：纯事件→岗位图。
- `build_unified_graph_view.py`：**融合队友的岗位-技能图谱 + 本模块事件**（复用 `export_graph_interactive_v2` 渲染器）。`--full` 全量、`--role` 单角色。
- **产出**：`reports/*_graph*.html`（双击打开）。

### `pipelines/trend/count_useful_events.py` — 规模统计
- 统计全量里过四重约束的"相关事件"有多少、按月/桶/角色分布。
- **怎么用**：`python -m pipelines.trend.count_useful_events`。

### `tests/unit/test_evidence_service.py` — 冒烟测试
- 四重约束闸门用合成数据测（CI 可跑）；检索结构在有索引时测。

## 8. 已知限制（数据决定的天花板）

1. GDELT **无标题/正文**，匹配多为关键词；存在同形词噪音（azure 云 vs 蓝宝石）。
2. 证据相关性**无法人工完全验证**（无正文）；故采用"聚合为主 + 干净样本为辅 + 诚实标注"。
3. JD `job_url` 源数据为空 → 降级为存在性证据。
4. `rerank()` 语义钩子留空——需上游提供文本后才有意义。
