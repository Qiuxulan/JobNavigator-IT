## 0. 职责与硬契约

你这个模块对外只有两个"硬接口"，其余实现自由：

1. **运行时检索接口**（`02_队友任务分工.md` §3 / §5.1 规定）

   ```python
   def retrieve_evidence(role: str, months: tuple[str, str], top_k: int = 5) -> list[dict]:
       """每条证据至少含 url, source_domain, tone, themes, match_weight。"""
   ```

2. **批量证据文件**（`docs/02-system-data/03-industry-data-schema.md` §5）
   `data/gold/trend_evidence_v1.jsonl`，每行 = 一个趋势结论 + TopK 证据，给 D 融合用。

3. **图谱事件边**（`docs/02-system-data/02-data-and-graph-design.md` §4）
   `AFFECTS(TrendEvent → JobRole)`，写入既有 `graph_nodes` / `graph_edges` 表。

核心设计原则：**一次"方向感知归因"选择 → 多处产出**。检索核心只有一份，运行时接口、批量 jsonl、图谱事件边都复用它，绝不重复实现检索逻辑。

## 1. 总体数据流

```
输入数据（data/raw, data/gold）
  ├─ gdelt_gkg_role_documents.jsonl   2.6GB / 172万条   事件语料
  ├─ processed_jd_jobs.json           170MB / 7万条     JD 存在性证据
  ├─ role_trend_scores.json (B)       340 条结论        待解释/待挂证据
  ├─ gdelt_impact_role_month_features 角色-月情绪/风险   方向信号
  └─ role_taxonomy.json               role_id↔canonical_role 映射
        │
        ▼  ① 离线索引层  pipelines/trend/build_evidence_index.py
   分区 Parquet + DuckDB（事件库 / JD 库）
        │
        ▼  ② 检索核心层  app/services/evidence.py  (EvidenceService)
   过滤(role+月) → 方向归因排序 → 混 JD → 去重 → TopK
        │
        ├─③A 运行时接口 retrieve_evidence()      → 组员3 Agent 工具
        ├─③B 批量生成 build_trend_evidence.py     → trend_evidence_v1.jsonl → D
        ├─③C API 路由 GET /evidence/{role}        → 前端
        └─③D 事件入图 build_event_graph.py        → graph_nodes/graph_edges
                                                    （AFFECTS 边）
```

**两个已知数据坑（写进代码要兜底）**：

1. `tone` 是逗号分隔 6 值串，第一值是综合情绪（-100~100），需解析取第一值。
2. `processed_jd_jobs.json` 的 `job_url` **全为空**——契约假设的"可点招聘链接"没有，JD 证据退化为"存在性证据"（company_name + raw_job_title + post_date + salary_mid）。

## 3. 分层架构（每层：做什么 / 怎么做 / 用什么 / 产出）

### 3.1 离线索引层 — `pipelines/trend/build_evidence_index.py`（新建）

- **做什么**：把 2.6GB jsonl 和 170MB JD 转成可快速按 (role, month) 过滤的列式索引，避免每次请求把 2.6GB 读进内存。
- **怎么做**：流式读 jsonl → 解析/清洗（tone 取第一值、themes 拆词）→ 写成按 `canonical_role` 分区的 Parquet；JD 同样转 Parquet。
- **用什么**：`duckdb` + `pyarrow`（流式、零额外服务）。**不用 ElasticSearch**——查询是"结构化过滤+排序"，不是开放式全文搜索，ES 的部署成本不划算。
- **产出**：`data/processed/evidence_index/events/*.parquet`、`.../jobs/*.parquet`（一次性可重跑）。

### 3.2 检索核心层 — `app/services/evidence.py`（新建 `EvidenceService`）

- **做什么**：给定 (role, 月区间) 选出最能解释该趋势的 TopK 证据。
- **怎么做（四步）**：
  1. **过滤召回**：DuckDB 按 `canonical_role` + `month` 区间查候选（毫秒级）。
  2. **方向归因排序**（核心）：复合分
     `composite = 0.4·主题相关(BM25) + 0.3·方向对齐 + 0.2·事件重要性 + 0.1·时间近度`
     - 方向对齐：trend_direction=up 偏好正 tone / 机会类 event_type；down 偏好负 tone / 风险类。
     - 事件重要性：source 覆盖数、tone 强度（压"随口一提"的噪音）。
     - B 的 `main_factors`（中文）映射到极性参与，不再当词分。
  3. **混入 JD 证据**：同角色 JD 作为 `evidence_type="job_posting"` 补充。
  4. **去重 + TopK**：按 url 去重取前 K。
- **用什么**：DuckDB（过滤）+ 纯 Python BM25（已实现，可移植）+ 可选 embedding 重排（仅对候选子集）。
- **产出**：`list[dict]`，每条含 `url, source_domain, tone, themes, match_weight`（契约最小字段）+ `title, published_at, retrieval_score, evidence_type, impact_direction`。

### 3.3 出口层（四个出口，共用 3.2 核心）

| 出口 | 文件 | 形态 | 消费方 |
|---|---|---|---|
| ③A 运行时接口 | `app/services/evidence.py` | `retrieve_evidence(role, months, top_k)` | 组员3 注册为 Agent 工具 |
| ③B 批量证据 | `pipelines/trend/build_trend_evidence.py`（已有，改成调核心） | `trend_evidence_v1.jsonl` | D 行业报告 |
| ③C API | `app/api/routes.py` | `GET /evidence/{role}` | 前端 |
| ③D 事件入图 | `pipelines/graph/build_event_graph.py`（新建） | AFFECTS 边 | 知识图谱页 |

另外：`app/services/trend.py` 的 `TrendService` 调 `EvidenceService` 填 `TrendSignal.evidence`，让 `/trend` 接口自带证据。

## 4. 图谱以什么方式接进去（重点）

### 4.1 接入点：复用既有表，零改库结构

既有 `pipelines/graph/build_career_graph_v2.py` 已经建好两张通用表：

```
graph_nodes(node_type, node_id, payload_json, feature_vector, embedding_vector, updated_at)  PK(node_type,node_id)
graph_edges(src_type, src_id, dst_type, dst_id, relation, weight, confidence, meta_json, source_time)
```

`node_type` / `relation` 都是自由文本，所以**只需新增** `node_type="event"` 和 `relation="AFFECTS"`，不动表结构、不碰队友的 career graph 代码。

### 4.2 选择层是单一事实源（不二次检索）

检索核心（3.2）为每个 (role, month) 选出的 TopK 因果事件，**就是**该挂到该岗位上的 AFFECTS 事件。所以入图不另跑检索——同一批选择结果，既写 `trend_evidence_v1.jsonl`，又写图谱边。

### 4.3 节点与边的构造

- **event 节点**：
  - `node_id` = url 的稳定哈希（同一条新闻跨多个角色只建一个节点，去重）。
  - `payload_json` = {title, url, source_domain, published_at, tone, event_type, bucket_name, themes}。
- **AFFECTS 边**（一个事件影响 N 个角色 = N 条边）：
  - `src_type="event"`, `src_id`=event node_id
  - `dst_type="job"`, `dst_id`=**role_id**（用 JD 自带的 role_id，或 role_taxonomy 映射 canonical_role→role_id）
  - `relation="AFFECTS"`, `weight`=composite 复合分, `confidence`=检索置信度
  - `meta_json` = {impact_direction, event_type, month, bucket_name}
  - `source_time` = 事件日期

### 4.4 阈值标定（务必处理）

设计 §4 写的是 `confidence≥0.6, weight≥0.5`。但实测 GDELT 的 `match_weight` 大多是 0.2，**硬卡 0.5 会让图谱几乎为空**。方案：**用检索核心的 composite（0~1，归一 BM25 能到 1）作为 `weight`**，阈值按当前数据分布重新标定（如取 composite 分位数 P60），并在评估报告里说明口径。

### 4.5 入图模块：`pipelines/graph/build_event_graph.py`

照 `build_career_graph_v2` 的写法，自管增量：先 `DELETE FROM graph_edges WHERE relation='AFFECTS'` 和对应 event 节点，再批量 INSERT。与 career graph 完全解耦，可独立重跑。

边质量完全取决于②的方向排序，所以②是重心，先把它在样本上调好再上全量。

## 7. 待对齐 / 决策项

1. **方向过滤软/硬**：建议软加权（保留少量反向事件支撑 risk_notes）。
2. **AFFECTS 阈值标定**：建议用 composite 当 weight，按分位数定阈值（见 §4.4）。
3. **job_url 为空**：JD 证据降级为存在性证据；需向组员1确认是否有带链接的版本。
4. **TopK 一致性**：jsonl 与图谱是否同一 K，还是图谱更严（只挂方向对齐最强 2~3 条）。
5. **全量月份覆盖**：建索引时确认 2.6GB 文件实际覆盖到 2026-05（样本只见 1 月）。

## 8. 技术选型小结

| 选型 | 决定 | 理由 |
|---|---|---|
| 存储/过滤 | DuckDB + 分区 Parquet | 2.6GB 不进内存、按 role+月毫秒过滤、零额外服务 |
| 是否上 ES | **不上** | 查询是结构化过滤+排序，非全文搜索；ES 部署成本不划算 |
| 关键词检索 | 纯 Python BM25（已实现） | 零依赖、可移植、作召回与主题相关分 |
| 语义重排 | 可选，仅候选子集 | 不给 172 万条全做向量，省算力 |
| 图谱接入 | 复用 graph_nodes/edges + AFFECTS | 表结构通用，零改库，与 career graph 解耦 |
