### 2.3 处理流程

```
Arrow/CSV 源文件
    │
    ├─▶ collect_hf_recruitment_jobs.py (IT 过滤 + 字段标准化)
    ├─▶ collect_ai_job_dataset_jobs.py (AI 角色过滤 + 字段标准化)
    │
    ▼
raw_jd_jobs_hf_recruitment.json / raw_jd_jobs_ai_job_dataset.json
    │
    ▼
standardize_jd_roles.py
    │  ├─ 读取 DB (失败则回退本地 JSON)
    │  ├─ score_role_match() — 多策略角色匹配
    │  │   ├─ 角色名精确匹配
    │  │   ├─ 别名模糊匹配
    │  │   ├─ 技能关键词匹配
    │  │   └─ 单 token 角色名匹配 (score=0.65)
    │  └─ choose_best_role() — 选最高分角色
    │
    ▼
processed_jd_jobs.json (70,826 条匹配结果)
    │
    ▼
build_jd_role_month_features.py
    │  ├─ 按月+角色 groupby 聚合
    │  ├─ 分源统计：hf_post_count / ai_post_count（独立统计）
    │  ├─ compute_source_demand_index()
    │  │   └─ z-score 归一化 → sigmoid 映射 → 分源需求指数
    │  └─ unify_sources() — HF(0.60) + AI(0.40) 加权融合
    │
    ▼
jd_role_month_features.json (2,398 行, 62 角色, 2020-01~2025-04)
```

### 2.4 角色匹配算法详解

`score_role_match()` 是匹配核心，采用多策略评分：

```
score_role_match(title, description, role)
    │
    ├─ 策略 1: 角色名匹配 (权重 0.30)
    │   └─ canonical_role 和 aliases 在 title 中的匹配
    │
    ├─ 策略 2: 技能匹配 (权重 0.40)
    │   └─ top_skills 在 title+description 中的命中率
    │
    ├─ 策略 3: 上下文匹配 (权重 0.20)
    │   └─ 相关关键词、行业术语匹配
    │
    ├─ 策略 4: 单 token 角色名 (权重 0.65)
    │   └─ 当角色名为单个词时（如 "Data Scientist" 是双词，跳过）
    │
    └─ 综合评分 = 各策略加权和 × 归一化
```

### 2.5 方案A：分源独立需求指数

为了解决 HF（2020-2023）和 AI（2024-2025）两个来源时间不重叠、数据量差异大的问题，采用**分源独立计算**方案：

**改前（问题）**：合并 `job_post_count = hf_post_count + ai_post_count` → AI 角色由于 AI 数据集的存在，post_count 被翻倍，导致 `jd_demand_index` 偏高。

**改后（方案 A）**：
```
hf_demand_index = sigmoid(zscore(hf_post_count))   ← 仅基于 HF 内部分布
ai_demand_index = sigmoid(zscore(ai_post_count))   ← 仅基于 AI 内部分布

jd_demand_index = 0.60 × hf_demand_index + 0.40 × ai_demand_index
                 (仅 HF 时期)     (仅 AI 时期)      (双源时期)
```

## 3. 第二部分：GDELT 新闻数据处理

### 3.1 概述

GDELT（Global Database of Events, Language, and Tone）是全球最大的开放新闻数据库。本模块通过本地 GKG（Global Knowledge Graph）文件，提取与 69 个 IT 岗位相关的新闻事件，计算情绪指数和冲击分数。

### 3.2 数据源

| 属性 | 值 |
|:----|:----|
| 来源 | GDELT GKG CSV 文件（已下载到本地） |
| 本地目录 | `data/GDELT/april/` |
| 文件数 | **158 个 zip 文件** |
| 时间范围 | 2026-04 ~ 2026-06（最新数据） |
| 数据量 | 处理后 7,363,736 条 bucket 记录 |

### 3.3 处理流程

```
158 个 GKG CSV zip 文件
    │
    ▼
process_gdelt_gkg_local.py
    │
    ├─ 步骤 1: 逐批解压 zip（每批 10 个）
    │
    ├─ 步骤 2: 主题桶过滤（5 个桶）
    │   ├─ ai_llm        → TECH_AUTOMATION, SOC_TECHNOLOGYSECTOR, ...
    │   ├─ data_platform → DATA, DATABASE, DATA_ENGINEERING, ...
    │   ├─ cloud_devops  → CLOUD, DEVOPS, KUBERNETES, ...
    │   ├─ security      → CYBERSECURITY, SECURITY, DATA_BREACH, ...
    │   └─ backend_platform → API, MICROSERVICES, BACKEND, ...
    │
    ├─ 步骤 3: 角色匹配（对应 69 个角色）
    │   └─ 使用角色名、别名、技能在 GKG 主题中匹配
    │
    ├─ 步骤 4: 情绪分析
    │   └─ GKG V2Tone 格式: "tone, positive, negative, ..."
    │   └─ 计算 sentiment_index, risk_index, opportunity_index
    │
    ├─ 步骤 5: 事件冲击评分
    │   └─ 基于文章数、来源多样性、情绪极端值计算 impact_score
    │
    └─ 输出 3 类产物
```

| security | CYBERSECURITY, SECURITY, DATA_BREACH 等 | 4 | 安全岗位 |

## 4. 第三部分：技术热度数据处理

### 4.1 概述

技术热度模块通过 GitHub 和 arXiv 两个技术社区 API，采集与 69 个 IT 岗位相关的技术趋势数据。每个角色的技能关键词被用作搜索查询，汇总为月度技术热度指标。

### 4.2 数据源

| 平台 | 接口 | 数据内容 | 时间范围 |
|:----|:----|:--------|:--------|
| GitHub API | `search/repositories` | 仓库数、Star 数 | 2026-01 ~ 2026-06 |
| arXiv API | `api/search` | 论文数 | 2026-01 ~ 2026-06 |
| Google Trends | — | ❌ 已禁用（无 API Key） | — |

### 4.3 处理流程

```
role_taxonomy.json (69 角色, 每角色含 top_skills)
    │
    ▼
collect_tech_heat.py
    │
    ├─ 步骤 1: 构建查询词
    │   └─ 为每个角色提取 canonical_role + aliases + top_skills 作为搜索项
    │
    ├─ 步骤 2: GitHub API 查询
    │   └─ 每项搜索最近 6 个月的仓库，统计 repo_count 和 stars
    │   └─ 使用 GitHub Token 鉴权
    │
    ├─ 步骤 3: arXiv API 查询
    │   └─ 每项搜索最近 6 个月的论文，统计 paper_count
    │
    ├─ 步骤 4: 关键词聚合到角色
    │   └─ 每个角色的多个搜索关键词，按权重加权平均
    │   └─ 权重分配: 角色名(0.15) + 别名(0.10) + 技能(剩余)
    │
    └─ 步骤 5: 噪音过滤
        └─ GENERIC_QUERY_STOP_TERMS 排除通用词
        └─ CATEGORY_SKILL_PENALTIES 降低泛化技能权重
```

### 4.4 噪音过滤机制

为防止通用技术词（如 "Python" 被所有角色匹配到）导致热度失真，实现了多层过滤：

**第 1 层 - 通用停止词**（完全排除）：
```
css, html, devops, ci/cd, microservices, rest api, sql, git,
agile, scrum, jira, ux, ui, leadership, communication, ...
```

**第 2 层 - 类别技能惩罚**（降低权重）：
```
Product Manager → scrum(0.02), jira(0.02), agile(0.03)
Business Analyst → sql(0.03), excel(0.02), tableau(0.03)
```

**第 3 层 - 角色名提示**（强化特定角色）：
```
"project manager" → 排除 devops/ci-cd/blockchain 噪音
"rust blockchain" → 强化 blockchain/solidity/web3 匹配
"frontend react" → 强化 react/jsx/css 匹配
```

## 5. 特征合并与模型数据

### 5.1 三源合并

`build_role_month_features.py` 将三个独立数据源合并为统一的 `role_month_features`：

```
JD 月特征 (jd_role_month_features.json)
    │  jd_demand_index, hf_post_count, ai_post_count, ...
    │
GDELT 月特征 (gdelt_gkg_role_month_features.json)
    │  gdelt_article_count, gdelt_sentiment_index, ...
    │
GDELT 冲击特征 (gdelt_impact_role_month_features.json)
    │  gdelt_event_impact_score
    │
Tech Heat 月特征 (tech_keyword_month_features.json)
    │  google_trend_index, github_repo_count, arxiv_paper_count
    │
    ▼
role_month_features.json (2,743 行, 69 角色, 2020-01~2026-05)
```

### 5.2 趋势评分

`score_role_trends.py` 使用加权评分系统为每个角色每月计算趋势方向：

| 特征 | 权重 | 说明 |
|:----|:----|:-----|
| jd_demand_index | 0.46 | JD 需求指数（主指标） |
| gdelt_opportunity_index | 0.16 | 行业机会类新闻 |
| gdelt_risk_index | -0.16 | 行业风险类新闻 |
| gdelt_sentiment_index | 0.08 | 新闻整体情绪 |
| gdelt_event_impact_score | 0.05 | 重大事件冲击 |
| github_repo_count | 0.05 | GitHub 仓库数 |
| arxiv_paper_count | 0.03 | arXiv 论文数 |
| remote_ratio | 0.02 | 远程岗位占比 |

**趋势方向**：`up`(≥0.58) / `flat`(0.42~0.58) / `down`(≤0.42)

**产出**：`role_trend_scores.json`（每个角色每月一条评分记录）

### 5.3 PatchTST 数据集

`prepare_trend_model_dataset.py` 将合并后的特征转换为时序预测模型所需的格式：

```
role_month_features.json
    │
    ▼
build_patchtst_panel()
    │
    ├─ 步骤 1: 确定时间窗口
    │   └─ lookback_months=77（覆盖全量 2020-01 ~ 2026-05）
    │
    ├─ 步骤 2: 构建面板
    │   └─ 69 角色 × 77 月 = 5,313 行
    │   └─ 空值填充为 0.0
    │
    ├─ 步骤 3: 添加 time_idx
```
