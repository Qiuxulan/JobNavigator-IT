# 第一部分 项目全貌

## 1.1 解决什么问题

IT 求职者（尤其是大学生）面临四个断层：
1. **信息断层**：岗位市场在变（AI 岗位爆发），但求职者看不到实时、本土化的市场全貌
2. **认知断层**：不知道自己现有技能和目标岗位的差距具体是什么
3. **路径断层**：知道缺什么，但不知道先学哪个、用哪份资料、学多久
4. **时效断层**：网上的职业分析和课程推荐往往是几年前的

## 1.2 系统闭环

```
看市场（实时数据看板）→ 选方向（岗位洞察对比）→ 测匹配（模型推荐）
→ 补技能（学习路径）→ 问助手（AI 答疑）→ 收藏跟踪（个人中心）
```

# 第二部分 数据层（原材料从哪来）

## 2.1 全球 JD 数据集：12.99 万条怎么来的

【输入】8 个公开数据源，全部是 Kaggle / HuggingFace 上的公开招聘数据集或官方 API，已下载到 `/data/shichaojian/JNIT/raw/jd/`：

| 数据源 | 是什么 | 角色 |
|---|---|---|
| zalizedata_tech_postings | 约 39 万行纯技术岗 JD，skills 列由 ATS（招聘系统）预抽取好 | 主源 |
| minmaxxxer 月度快照 | 每月全量招聘快照，字段规整但不纯是 IT | 月度增量主源 |
| nextgig_multi_ats | 多 ATS 聚合，字段最全但日期缺失率高 | 补充 |
| makenomistakes_9ats | 9 个 ATS 的纯技术岗小数据集 | 补充 |
| jobicy_remote | 远程岗位 JSONL | 补充远程岗 |
| live_api | 我们自己每月调 Remotive + Jobicy 的公开 API 抓当月岗位 | 当月实时增量 |
| JOA 雇主直采月度快照 | JobOpportunitiesAPI 数据集（CC-BY-4.0 许可证，允许署名使用），first_seen 作发布日期 | 月度增量 |
| HN 招聘帖（另见 2.4） | 需求侧信号 | 补充 |

【步骤】`pipelines/extract/unify_jd_v3.py` 做四件事：
1. **统一字段**：8 个源的字段名、格式完全不同，统一映射到 职位名/描述/薪资/日期/地区/公司/工作方式 这套 schema（数据模式定义）
2. **IT 过滤**：非纯技术源（如 minmaxxxer）用职位名白/黑名单正则过滤，只留 IT 岗
3. **去重**：按职位名+公司+描述哈希去重
4. **按月分区**：按发布月份切成 Parquet 文件（Parquet：列式存储格式，同样数据比 CSV 小 5-10 倍、读取快），无法解析日期的进 `unknown` 分区

【窗口】2023-10 至 2026-10，共 37 个月。国内岗位占比 < 1%（海外为主）——**这正是我们另建国内实时数据层的原因**（见 2.2）。

【效果】129,897 行，QC 报告在 `_qc_report.json`。每月 3 号由 cron 自动跑增量。

## 2.2 国内实时岗位：我们的差异化数据层

【为什么做】公开 JD 数据集几乎全是海外的；BOSS 直聘/拉勾/智联等国内平台都有强反爬（登录态、滑块、加密），不能合法稳定地抓。**公司官网招聘页的公开 JSON 接口是合法、稳定、结构化的折中**。

【来源】43 个采集源（2026-11-10 一天内从 6 家扩到 43 个），分五类：
- **自建接口（6 家）**：腾讯、字节跳动、百度、美团、网易、京东
- **飞书招聘托管（13 家）**：小米、蔚来、小鹏、Momenta、商汤科技、零一万物、小马智行、库洛游戏、叠纸游戏、美图、轻舟智航、极兔速递、永辉超市。发现方法：构建 168 个公司拼音 slug 字典，批量探测 `*.jobs.feishu.cn` 托管域名，命中即复用与字节同套的接口
- **阿里系子集团（15 家）**：高德、阿里云、饿了么、夸克、钉钉、菜鸟、灵犀互娱、平头哥、盒马、通义、淘天集团、阿里健康、阿里国际、阿里控股、虎鲸文娱。突破过程：阿里主站 talent.alibaba.com 只是导航页，用 playwright 渲染发现真实岗位分散在 15 个子集团站点；进一步抓包发现其反爬是 Spring 标准 XSRF 机制（先 GET 列表页拿 cookie，再以 `_csrf` 参数调接口），**纯 requests 即可复现，每日采集不需要浏览器**
- **飞书二轮爆破（8 家）**：得物、面壁智能、中科创达、英雄游戏、霸王茶姬、寺库、创梦天地、四维图新
- **国聘平台聚合（1 源抵千家）**：国聘是央企国企招聘主平台。其签名接口（/api/jobs/v3）我们没有硬啃，而是用 playwright 观察真实页面行为发现了免签名的人才推荐接口（recom-job），按 24 个 IT 关键词分页抓取去重，单次采集 5,291 个岗位。字段比官网还全：**月薪上下限、学历、经验、完整 JD 正文**——这是项目第一次有国内薪资数据。雇主名为真实企业（航天科工、中材国际这类），公司维度统计按真实雇主计算，不生成「国聘」伪公司卡片
- **探测黑名单**（都试过、确认拿不到，记录在 `docs/2026-11整理记录.md`）：快手（需内部鉴权）、拼多多（403 反爬）、B 站（登录态）、小红书（无公开接口）、知乎/大疆（Moka 平台响应体加密）、华为/滴滴/米哈游（无公开列表接口）、飞猪（不下发 XSRF cookie）、中国公共招聘网（连接超时）

【步骤】`pipelines/cn_jobs/collect.py` 每天跑一次（cron 07:30）：
1. 逐公司翻页拉全量岗位列表（限速 0.4 秒/请求，礼貌访问）
2. **IT 过滤**：三层规则——非 IT 岗位名黑名单（销售/客服/门店…）、IT 岗位名白名单（工程师/算法/数据…）、职能类别白名单；带"运营"字样但实为研发岗的（如"运营平台开发工程师"）用强 IT 词救回
3. **国内过滤**：城市名命中海外城市表（新加坡/伦敦/东京…）的剔除
4. **逐日累积**（核心设计）：每个岗位记 `first_seen`（首次出现日）和 `last_seen`（最后出现日）。今天还在 = 在招；昨天在今天不在 = 下架。**单日快照逐日累积成时间序列，国内招聘趋势是我们自己测出来的，不引用别人报告**
5. 聚合：`build_market.py` 产出在招数、公司/城市/方向分布、技能需求榜、每日序列

【效果】43/43 源全部成功，在招 IT 岗位 21,617 个（2026-11-11 口径，42 家官网 + 国聘聚合），技能覆盖率 83.2%。单源失败只影响自家数据，主链路永不断更。字节跳动接口单次最多返回 1 万条，实际在招更多。

## 2.3 行业新闻与海外信号

- **新闻**（`pipelines/news/collect.py`，每 3 小时）：14 个来源——中文：IT之家、InfoQ中文、开源中国、Solidot、cnBeta、掘金、GoogleNews 订阅的 36氪/机器之心；英文：Ars Technica、The Verge、TechCrunch、HackerNews、layoffs.fyi、GitHub Trending。URL 归一化（去跟踪参数）后按哈希去重入 PostgreSQL
- **WARN 裁员**：美国《工人调整和再培训通知法》要求 100 人以上裁员提前 60 天向州政府申报，数据法定公开。来源是 HuggingFace 上按日更新的 WARN 备案数据集（作者已预筛科技公司），我们再用 IT 雇主关键词复核，按月+公司聚合。1748 条。**法定数据，可信度最高**
- **海外公司在招**：25 家头部科技公司（OpenAI/Anthropic/NVIDIA/Stripe 等）的逐日在招岗位数（roletrends 数据集），算 7 日/30 日净增动量，按行业分组（AI/数据云/金融科技/开发者工具…）
- **HN 招聘帖**：HackerNews 每月 1 号的"Who is hiring"帖，评论是半结构化的"公司|岗位|远程|薪资"文本，用 Algolia HN 公开 API（免认证）解析，已回填 2025-01 至今 23 个月

## 2.4 学习资源：2006 条怎么筛出来的

【来源六类】
1. Coursera / freeCodeCamp 等国际平台的免费课程
2. B 站课程（中文优先）
3. GitHub 高星实战项目合集：解析 project-based-learning、build-your-own-x、realworld 三个知名仓库的 README，按章节标题（语言/技术）映射到技能，每节最多取 14 个
4. 云厂商官方认证/免费学习路径（收录前逐一验证可达）
5. 免费合法在线书籍/官方文档
6. 中文定向补充：v4 质检发现 34 个热门技能缺中文资源，定向补菜鸟教程/廖雪峰/中文官方文档等

【筛选指标】来源权威性、是否免费、语言（中文优先）、时效（版本不过时）、**链接活性**（v5 采集时统一跑 HTTP 检查，失效自动剔除，抽查直连率 92.5%）。

【产物】`learning_resources_v5.json`，162 门课含章节结构（章节级挂载到技能，路径里可以精确到"学这门课的第 3-5 章"）。

# 第三部分 技能体系（词表 + 抽取）

## 3.1 词表 v1 → v2 → v4 的完整演进

**v1（275 个技能）**：项目初期人工维护的词表，每个技能 = 规范名 + 别名表（kubernetes ↔ k8s）。问题：覆盖面窄，2024 年后的新词（LLM/RAG/MCP）没有。

**v2（295 个技能）**：`pipelines/foundation/build_skill_vocab_v2.py`，v1 全部保留（id 不变，向后兼容），融合三个外部源：
1. **O\*NET 31.0**（美国劳工部官方职业数据库）的 software_skills 表——权威技术名 + "Hot Technology / In Demand"（热门/紧缺）官方标记
2. **Tabiya ESCO v1.1.1**（欧盟官方技能库的开放数据版）——用 preferredLabel/altLabels（标准名/别名表）扩充别名
3. **25 万行 JD 的真实技能列频次**——真实在用的证据

融合规则（阈值都是"宁缺毋滥"原则定的）：
- JD 里出现但 v1 没有的词，频次 **≥200** 的拿去和 O*NET/ESCO 匹配，命中则吸收其别名并继承热度标记
- 匹配不上但频次 **≥500** 的，过 IT 相关性过滤（黑名单剔软技能/商务词/公司名噪声 + 白名单 + 词形规则）后成为新技能
- 总规模上限 400（v1 的 275 + 新增 ≤125，按频次截断）
- 旧 275 技能用 O*NET Hot Technology 校准热度、用 ESCO 补别名（每技能最多补 8 个，别名长度 ≤40 字符 ≤6 词，防长尾垃圾）

**v4（+161 个技能的增量词表）**：三步走——

第 1 步「造候选」：`extend_skill_vocab_onet.py` 从 O*NET/ESCO 里筛出 v2 没覆盖的候选 910 条。

第 2 步「LLM 审核」：`review_skill_vocab_v3.py` 把 910 条候选按 50 条/批发给 DeepSeek，用严格 prompt 审核（prompt 原文在代码里）：
- keep=true 的唯一标准：是真实、具体的 IT 技能/工具/框架/平台/数据库/云/AI 产品/协议/方法，且可能出现在 JD 里（正面例子：Splunk Enterprise、Apache Tomcat）
- 判 false 的：宽泛软技能（"遵守商业道德""团队协作"）、非 IT 通用词、过短歧义词（go/c/r/data）、宽泛伞词（"web application software"）
- 同时让 LLM 输出归一化规范名（小写、去版本号）、别名表、类别、一句理由
- 工程细节：JSON mode 强制结构化输出；每批 schema 校验失败重试 3 次（指数退避）；进度增量落盘，中断可续跑
- **结果：keep 174 条（19.1%），drop 736 条**——81% 被淘汰，说明审核真的在过滤，不是橡皮图章

第 3 步「合并」：`build_skill_vocab_v4.py` 把 keep 的 174 条合并进增量词典，再做一轮机器校验：
- 规范名已被 v2 覆盖的整条跳过（11 条）
- 别名与 v2 已有映射冲突的丢弃该别名（先到先得，180 个别名被丢）
- 过高风险别名黑名单（access 是动词"访问"、word、teams、scratch 会误匹配普通文本）
- LLM 放行但人工复核认定垃圾的整条丢弃（8 条，如 "online job platforms" 根本不是技能）
- 最终：**161 个新技能、407 个别名**

## 3.2 技能抽取：怎么从 JD 文本里抽出技能

【做法】规则词典匹配（`pipelines/extract/enrich_skills_v3.py`），不用大模型逐条抽——12.99 万条 JD 调 LLM 太贵太慢，规则快、可控、可复现。

机制细节：
1. 词表全部别名编译成一个超大正则，**词边界匹配**（防止 "c" 匹配到 "abc" 里的 c、"c++" 匹配到 "c++17"）
2. **歧义屏蔽表**：go/c/r/data/rest/cv/unity 这类短词即使带词边界也是常见英语单词，显式屏蔽它们的裸别名；但这些技能的具体别名不受影响（golang、c语言、rest api 照常被识别）
3. JD 描述截取前 8000 字符（太长的 JD 尾部通常是公司介绍）
4. ATS 已带 skills 列的行直接用；skills 为空的行用上述规则从描述里补抽，并打 `skills_enriched` 标记
5. 国内 JD 另加一张中文同义词表（大模型→llm、K8s→kubernetes、数据仓库→data-warehouse 等 38 组）

## 3.3 "86.8% 的 JD 能抽取出技能"是怎么测的

【定义】技能覆盖率 = skills 列非空的 JD 行数 ÷ 总行数。注意是"至少抽到一个技能"，不是"抽全"。

【测量方法】`pipelines/extract/eval_skill_vocab_v4.py` 对 **129,897 行全量**（不是抽样）分别用 v3 口径和 v4 口径计算：

| 口径 | 非空率 | 平均每 JD 技能数 | 技能总命中 | 独立技能数 |
|---|---|---|---|---|
| v3 | 86.63% | 5.392 | 700,450 | 33,950 |
| v4 | **86.83%** | 5.395 | 700,779 | 33,972 |

v4 净增 +0.2 个百分点，265 行 JD 因 v4 新词首次获得技能标注。增幅小是预期内的——v2 主词表已经覆盖了高频技能，v4 的价值在于长尾新技术（如 Splunk、OpenShift）能被识别。

【回归保证】固定随机种子 42 抽 1000 行，检查"v3 抽到的技能是否全部仍在 v4 结果里"——**丢失 0 行**。这保证词表升级不会让任何已有结果变差（只能变好）。

# 第四部分 岗位体系（99 个岗位 + 画像）

## 4.1 99 个岗位是怎么定的

**不是拍脑袋列的，是"人工体系 + 数据驱动扩充"：**

1. **v2 的 91 岗**：早期人工定义 + 聚类校对的细粒度岗位体系，每岗带 search_keywords（搜索关键词）和 example_titles（真实职位名例子）
2. **title→role 映射**（`expand_roles_v3.py`）：把 12.6 万条 JD 的职位名归一化后映射进 91 岗：
   - 最长关键词优先 + 词边界匹配（"senior" 这类资历前缀天然被子串匹配覆盖）
   - **跨岗关键词去重**：同一个关键词出现在多个岗位时，按"关键词 token 与岗位名的重叠度"定唯一属主（修复过 "forward deployed engineer" 同时挂在两个岗位下导致全部错位的问题）
   - **泛化词停用表**：other/qa/security/c++/java 这类单词太短或跨半数以上岗位，没有区分度，不参与匹配
3. **数据驱动扩充**：映射不上的职位名里，JD 数 **≥150** 的人工归簇成新岗位（阈值理由：低于 150 的岗位画像统计不可靠），从 role_090 续号。共新增 8 个（如 Site Reliability Engineer 1056 条 JD、Backend Engineer (General)）
4. **结果：91 + 8 = 99 岗**；QC 报告在 `expand_roles_v3_qc.json`

【一个要诚实回答的点】按职位名精确映射的 JD 行覆盖率是 41.8%——剩下的 58% 是长尾职位名（87,000 种不同写法），它们不进岗位画像统计。这是刻意选择：**宁可少统计，不可错归类**（画像质量优先于覆盖量）。

## 4.2 国内岗位的归类（另一套逻辑）

国内 JD 是中文的，走 `build_market.py` 里的 **60+ 条中文规则**，按优先级顺序命中第一条：
- 举例：`大模型|LLM|AIGC` → AI 应用工程师；`渗透|攻防|红队` → 渗透测试；`数据仓库|数仓|ETL` → 数据工程师；`Vue|前端|H5` → 前端开发……
- 全都没命中 → 兜底"通用软件工程师"
- 当前口径（含国聘）：**75.2% 归到具体细分岗位**，24.8% 落兜底——国聘的国企岗位名更多样（如「系统集成岗」），拉低了比例，规则表可持续补充。规则表在代码里公开可查、可持续补充

## 4.3 岗位画像：每个岗位的"档案"怎么算的

`build_role_profiles_v3.py` 对每个岗位从归属 JD 统计（`role_profiles_v3.json`）：

| 字段 | 算法 |
|---|---|
| skill_freq 技能频率 | **近期加权频率**：指数衰减，半衰期 12 个月（2026 年的 JD 权重远高于 2024 年——市场要什么技能是有时效性的） |
| core/required/optional | 按加权频率分档：core = top10 且 ≥0.10；required = ≥0.15；optional = 0.05~0.15。决定路径里"必学/应学/可选" |
| salary | 中位数/25/75 分位（美元年薪，取 JD 薪资区间中点；**样本 <10 不输出**，防小样本误导） |
| trend_momentum 趋势动量 | 近 3 月岗位份额均值 ÷ 之前 3 月均值 − 1。用份额不用条数，抗采集量波动 |
| jd_count / jd_count_6m | 总 JD 数 / 近 6 月 JD 数 |
| remote_ratio / 资历分布 | 远程比例、senior/junior 分布 |
| low_confidence | jd_count < 50 的岗如实标注低置信度 |

# 第五部分 模型原理详解（每个模型：原理 → 为什么选它 → 在项目里怎么用）

> 这部分是评委追问"你这个模型是什么原理"时的答案库。每个模型按统一格式：
> 【原理】（不堆公式，讲直觉）→【为什么选它】→【在项目里用在哪、输入输出是什么】。

## 5.1 向量嵌入模型：Qwen3-Embedding-4B

【原理】
- **Embedding（向量嵌入）**：把一段文本变成一串数字（向量），比如 2560 个浮点数。训练目标是让"意思近"的文本向量也靠近、"意思远"的离得远。这样"会 Python 和后端开发"和"后端工程师"即使字面完全不同，向量也很接近——**这是语义匹配而不是关键词匹配**
- 训练方法叫**对比学习（Contrastive Learning）**：给模型看成对的文本（相关/不相关），相关的拉近、不相关的推远，反复训练后形成一个"语义空间"
- **余弦相似度（Cosine Similarity）**：衡量两个向量夹角。夹角小→方向一致→语义相似。取值 -1 到 1，我们的场景里基本在 0.5~0.85
- Qwen3-Embedding-4B 底层是 Transformer（大语言模型同款架构，"4B" = 40 亿参数），把整段文本的上下文都考虑进去编码

【为什么选它】
- MTEB 榜（国际权威的多语言向量模型评测）前列，**中英文都强**（我们的用户画像是中文的）
- **可以本地部署**在我们的 GPU 上，一次下载永久免费；相比之下调 OpenAI embedding API 每次都要钱
- 淘汰了 JobBERT（2021 年英文模型，不懂中文简历和 AI Agent 这类新岗位）和 SBERT（更老、性能更差）

【在项目里】
- **输入**：用户画像拼成的一段查询文本（技能 + 目标岗位 + 经验描述）
- **输出**：一个 2560 维向量
- 99 个岗位的描述向量**离线预计算**好，存在 pgvector（见 5.2）；线上只做 1 次编码 + 1 次检索，毫秒级
- 岗位匹配链的第②步，见第六部分

## 5.2 向量数据库：pgvector

【原理】PostgreSQL（开源关系型数据库）的向量检索插件。给表加一种 `vector(2560)` 的列类型，支持按余弦距离找"最近的 N 个邻居"。本质是近似最近邻检索（ANN），毫秒级返回。

【在项目里】`job_roles.embedding` 列存 99 个岗位的向量；线上查询就是一句 SQL：`ORDER BY embedding <=> 用户向量 LIMIT 10`。选它而不是专用向量库（Milvus/FAISS 服务）的原因：99 个岗位的数据量用不上重型方案，pgvector 和主库一体、运维为零。

## 5.3 梯度提升树：LightGBM（LTR 学生模型的骨架）

【原理】
- **决策树**：一连串 if-else（"覆盖率>0.5？→ 是 → 语义分>0.6？→ …"），单棵树能力弱但可解释
- **梯度提升（Gradient Boosting）**：几百棵树**接力纠错**——第 1 棵树先预测，第 2 棵专门学第 1 棵的残差（错在哪），第 3 棵学前两棵的残差……最终预测 = 所有树相加。每棵新树都在修前面犯的错
- **LightGBM** 是微软实现的高效版本：直方图加速（把连续特征分桶）、按叶子生长（优先分裂收益最大的叶子），比传统 XGBoost 快数倍

【为什么选它】结构化表格数据（我们这种 21 个数值特征）上，树模型通常打赢神经网络；训练秒级、推理微秒级、**特征重要性可以直接读出来**（哪棵树用了哪个特征多少次）。

【在项目里】LTR 排序的学生模型本体，模型文件 `models/ltr_ranker_v1.txt`。特征重要性前五：目标岗位名匹配 > 公式原始分 > 语义分 > 覆盖率 > 薪资。

## 5.4 排序学习目标：LambdaRank

【原理】普通模型学的是"这个候选该打多少分"（逐点回归）；**LambdaRank 学的是"A 应该排在 B 前面"（逐对比较）**：取所有"相关度不同"的候选对，计算交换它们位置会让 NDCG（排序指标）变化多少，把这个变化当梯度直接优化排序质量。它是微软为搜索引擎发明的经典 LTR（Learning to Rank，学习排序）算法。

【为什么选它】我们的问题本质是排序（把最合适的岗位排前面），不是打分预测。NDCG 本身不可导没法直接优化，LambdaRank 是优化它的标准代理方法。

【在项目里】LightGBM 的 `objective=lambdarank`；2500 条 DeepSeek 标注的 0-3 分标签就是训练信号。完整流程见第六部分第⑤步。

## 5.5 知识蒸馏（Knowledge Distillation）：小模型怎么学大模型

【原理】大模型（教师）能力强但慢/贵/黑盒。蒸馏 = 让教师对大量样本输出判断，小模型（学生）以这些判断为教材训练。妙处在于学生学到的不只是答案，还有教师的"不确定性和相对偏好"（哪个比哪个好一点），而且海量样本平均下来，**教师单次判断的随机错误会被平滑掉**——这就是学生偶尔反超教师的原因。

【在项目里】DeepSeek 是教师（离线打 2500 条分，一次性花几块钱），LightGBM 是学生（线上永久免费、<1 秒、特征可解释）。**把"每次推荐都要调 API"变成了"一次性付费，终身本地运行"**。同样思路还用在了词表审核（O*NET/ESCO 910 候选 → DeepSeek 审核留 174）和先修图构建（三路 LLM 建图投票）。

## 5.6 时序基础模型：Chronos-Bolt（趋势预测主力）

【原理】
- 亚马逊 2024 年发布的**时间序列基础模型**：把"预测时序"变成"语言建模"问题——把历史数值离散化成一个个 token（类似文字），用 T5（一种 encoder-decoder 架构的 Transformer）在**几亿条真实时间序列**上预训练
- **零样本（Zero-shot）**：对一条它从没见过的序列（比如"RAG 技能的 JD 份额"），不用任何专门训练，直接预测未来
- 输出是**分位数预测（quantile）**：同时给出 10%/50%/90% 三条线（悲观/中性/乐观），我们取 50% 中位数当点预测

【为什么选它】
- 对比对象：旧版用的 PatchTST（另一种时序 Transformer）需要每条序列单独训练，且我们早期数据时间顺序有缺失，效果崩塌——这是当初推翻它的原因
- Chronos 不用逐序列训练、对缺失月份鲁棒、本地 GPU 推理实测峰值显存仅 106MB（极省）
- 回测中位 MAPE 0.307，比最强经典方法 Holt 低 17.7%（协议与数字见第八部分）

【在项目里】207 个有预测的技能中 111 个用它做 6 个月份额预测（其余 96 个回测不如经典方法，继续用 Holt/naive——逐技能选模，不打平换人）。

## 5.7 经典基线：naive / Holt / EMA / 季节法

【原理】这些统计方法是我们衡量一切花哨模型的"及格线"：
- **naive（朴素法）**：预测 = 最近一期值。最弱但最难彻底击败的基线
- **指数平滑（EMA/Exponential Smoothing）**：历史加权平均，越近的数据权重越大（权重按指数衰减）
- **Holt**：在指数平滑上加一个"趋势项"（在涨就外推继续涨）
- **damped Holt（阻尼 Holt）**：给趋势乘一个小于 1 的衰减系数——防止"连涨 3 个月就线性外推到无穷大"这种发疯预测
- **季节法**：预测 = 去年同月值（捕捉年度周期）

【在项目里】三个角色：①评估基线（新模型必须赢过它们才准上岗）；② fallback（96 个技能的在线预测仍用它们）；③岗位级预测的候选模型池（99 岗 × 5 模型逐岗回测选模）。

## 5.8 图神经网络：GraphSAGE（技能关系向量）

【原理】
- 把技能看成一张**图**：节点是技能，边是关系（先修、同属一岗、常被同时要求）
- **GraphSAGE（Graph Sample and Aggregate）**：每个节点不断"采样邻居的向量 → 聚合 → 更新自己"，迭代几轮后，每个技能的向量编码了它在图上的位置——**图上相近的技能，向量也相近**
- 和普通文本向量不同，它学的是"结构关系"而非"字面语义"

【在项目里】模型在 `models/graphsage_v2/`。两个用途：①学习路径的**可迁移折算**——"会 Java 学 Go 打折"的折扣力度就是 Java 和 Go 向量的余弦相似度；②知识图谱页面的技能关联展示。

## 5.9 大语言模型 DeepSeek 的三种角色

【原理】DeepSeek 是国产大语言模型（LLM：在海量文本上预训练的生成式模型），通过 OpenAI 兼容 API 调用。我们用它的三种能力：
1. **审核员**（离线）：词表 910 候选 → 留 174。JSON mode（强制输出合法 JSON，程序可解析）
2. **标注教师**（离线）：LTR 的 2500 条 0-3 分标签、先修图三路建图（365 次调用，2.16 元）
3. **在线助手**（在线）：**Function Calling（函数调用）**——我们不让它凭记忆回答，而是给它 14 个"工具"（查趋势/查岗位/算匹配/搜新闻……）的接口说明书，模型自己决定调哪个、传什么参数，拿到真实数据后再组织回答。最多 8 轮循环，temperature=0.3（低随机性，回答稳定可复现）

【设计原则】**LLM 只用在"一次性离线"或"可降级"的环节**。线上关键路径（匹配排序）不依赖任何 API——LLM 挂了，助手降级为关键词模板回答，匹配照样 <1 秒出结果。

## 5.10 统计方法小词典（散布在各模块）

- **p5/p95 分位数**：把所有分数排序，第 5%/95% 位置的值。比 min/max 抗极端值，用于校准锚点
- **sigmoid**：S 形曲线函数，把任意实数平滑压到 0-1 区间。用于趋势动量归一化（在涨的岗位 >0.5，在跌的 <0.5，且不会爆表）
- **Kendall's τ（肯德尔秩相关）**：衡量两个排序一致性的统计量。我们用它测路径个性化程度（不同用户路径顺序差异越大越好）
- **配对 t 检验（paired t-test）**：判断"同一批对象在两种方案下的差异"是不是运气。p<0.05 视为显著（我们路径实验 p<0.001）
- **MAPE（平均绝对百分比误差）**：|预测−实际|÷实际 的平均。0.307 意味着典型误差约 31%
- **交叉验证（Cross Validation）**：把数据切成几份轮流当考试集，防止模型"背答案"。LTR 用 5 折，时序用滚动原点（时间不能泄露，只能"用过去预测未来"）

# 第六部分 岗位匹配链（核心中的核心）

## 6.1 总流程（线上真实发生的六步）

```
用户画像（技能列表/简历文本、目标岗位、年限、学历）
 ① 拼查询文本：技能 + 目标岗位 + 经验描述拼成一段自然语言
 ② Qwen3-Embedding-4B 编码成 2560 维向量
 ③ pgvector 余弦相似度召回 top 10 候选岗位
 ④ 每个候选跑 analyze_role 算四个分项（覆盖/语义/趋势/可行性）
 ⑤ 排序：本地 LTR 模型（默认）/ DeepSeek 精排 / 公式，三选一可切换
 ⑥ 分数校准 + 置信度标注 → 输出：岗位 + 匹配度% + 置信度 + 技能缺口
```

## 6.2 第①②③步：语义召回

- **Embedding（向量嵌入）**：把文本变成数字向量，"意思近"的文本向量也近。相似度用余弦（两向量夹角的余弦，-1 到 1，越大越像）
- **Qwen3-Embedding-4B**：阿里 2025 年发布的向量模型，40 亿参数，中英文都强，MTEB 榜（国际权威向量模型评测）前列。**本地部署在 GPU 上，不花 API 钱**
- 为什么不用 JobBERT：2021 年的英文模型，对中文简历和新兴岗位（AI Agent 工程师）理解差；为什么不用 SBERT：同样过时
- 99 个岗位的向量预先算好存 pgvector（PostgreSQL 的向量检索插件），线上只做 1 次编码 + 1 次向量检索，毫秒级
- **召回 10 个候选**（top_n = max(10, top_k)）。评估证明 Hit@5 已是 1.0，10 个候选足够覆盖正确岗位

## 6.3 第④步：四维分项

每个候选岗位调 `analyze_role` 算四个 0-1 分项：
1. **coverage_weighted 技能覆盖**：用户已会技能 ∩ 岗位要求技能，按 JD 频率加权（覆盖高频技能比覆盖冷门技能加分多）
2. **semantic 语义分**：用户向量与岗位向量的余弦
3. **trend_momentum_norm 趋势分**：岗位趋势动量过 sigmoid 归一（在涨的岗位 >0.5，在跌的 <0.5）
4. **learning_feasibility 学习可行性**：1 − min(1, 补齐缺口所需学时/600h)——缺口太大学不完的岗位降分

## 6.4 第⑤步（关键演进）：公式 → LLM 精排 → 本地 LTR

**公式版（v3.1）**：`score = 0.15×覆盖 + 0.70×语义 + 0.15×趋势 + 0×可行性`。
权重不是拍的：`experiments/tune_ranking_weights.py` 在 58 例评估集上做网格搜索（语义权重 0.3~0.7 按 0.05 步长扫，四维权重和为 1），按 NDCG@5 选优。可行性权重最终调到 0——数据显示它对区分度没贡献。

**LLM 精排（v4）**：把 10 个候选给 DeepSeek 重新排序。效果好（Hit@1 0.983）但每次调用 15-30 秒、花钱、是黑盒、API 挂了就降级。

**LTR 蒸馏（v6，当前线上默认，本项目最大技术亮点）**：
- **思想：知识蒸馏（Knowledge Distillation）**——让小模型模仿大模型的判断，把大模型的能力"蒸"进一个本地小模型
- 具体三步：
  1. **造学生教材**：程序合成 250 个虚拟用户画像（按 12 个岗位大类分层采样保证多样性，年限 0/1/2/3/4/6/8/10/12 年离散取值）
  2. **请老师批改**：每个画像取 top10 候选，DeepSeek 给每个"画像-岗位"对打 0-3 分相关度（0=无关，3=高度相关），共 250×10=2500 条标签。标签分布 0分345条/1分1423条/2分543条/3分189条——有区分度，不是全打高分。调用 250 次 API，花费几块钱
  3. **训练学生**：LightGBM（微软的高效梯度提升树：几百棵决策树接力，每棵纠正前面树的错误）+ LambdaRank 目标函数（专门优化排序质量而非单点分数）
- **21 个特征全部本地可算、全部可解释**：目标岗位名精确匹配、公式原始分、校准后语义分、加权覆盖率、薪资对数、近 6 月 JD 量对数、缺口技能数、可迁移技能数、用户年限、学习学时……（完整清单在 `app/services/ltr_ranker.py` 顶部注释，训练/采集/推理三方共享同一份清单防错位）
- **特征重要性前五**：目标岗位名匹配（1622）> 公式原始分（1243）> 语义分（538）> 覆盖率（473）> 薪资——模型自己学到的规律和人工经验一致，互为印证
- **5 折交叉验证**（把数据分 5 份轮流当考试集）：graded NDCG@5 = 0.937

**三种方案效果对比（58 例人工评估集）**：

| 方案 | Hit@1 | NDCG@5 | MRR | 速度 | 成本 |
|---|---|---|---|---|---|
| 手工公式 | 0.793 | 0.695 | 0.888 | <1s | 0 |
| **本地 LTR（线上）** | **1.000** | 0.774 | **1.000** | **<1s** | **0** |
| DeepSeek 教师 | 0.983 | 0.782 | 0.991 | 15-30s | 按次付费 |

- 小模型反超老师的原因：评估集只有 58 例，教师单次调用有随机波动；蒸馏等于对教师的多次判断做了"平均去噪"。NDCG@5 上教师仍微弱领先（0.782 vs 0.774），我们如实汇报
- 环境变量 `JOBNAV_RANKER` 可切换 ltr/llm/formula，模型文件缺失自动回退公式——**永远有兜底**

## 6.5 第⑥步：校准与置信度（诚实展示）

**问题**：Qwen3 的原始余弦分挤在 0.50~0.85 窄带（p5=0.537，p95=0.742，基于 1740 个画像-岗位对统计），直接显示"62%"用户无法区分好坏。

**校准**：`sem_cal = clip((raw − 0.5365) / (0.7423 − 0.5365), 0, 1)`，把 p5/p95 两个锚点线性拉伸到 0-1，区分度提升 2.9 倍。

**关键设计（评委可能追问）**：**排序用原始分，展示用校准分**。因为校准是单调变换，列表内部顺序不变；但综合分是 0.15×覆盖+0.70×语义+0.15×趋势的加法组合，如果语义分先校准再相加，跨岗位顺序会变（实测 Hit@1 会动）。所以排序键严格保持校准前口径——"分数拉开了，但推荐顺序一个都不变"，有逐位一致性回归测试（`matching_v5_calibration_eval.json`，order_invariance: identical）。

**置信度三档**（规则公开写在 `score_calibration.py`）：
- 高：覆盖率 ≥0.5 且校准语义分 ≥0.6 且直接命中技能 ≥3 个
- 中：覆盖率 ≥0.25 且语义分 ≥0.4
- 低：其余（如实告诉用户"仅供参考"）

## 6.6 指标词典（答辩必背）

- **Hit@1（首位命中率）**：58 个测试用户里，正确答案出现在推荐第 1 位的比例
- **NDCG@5（归一化折损累计增益）**：前 5 个推荐的排序质量——相关岗位排越靠前得分越高，归一化到 0-1。比 Hit@1 更严格，因为它考察整个前 5 名的顺序
- **MRR（平均倒数排名）**：第一个正确答案排第几的倒数平均。排第 1 得 1 分，排第 2 得 0.5 分
- **评估集**：58 个手工构造的测试用户（18 + 40 两批），每个标注了正确的目标岗位

# 第七部分 学习路径规划（v4）

## 7.1 技能先修图：443 条"先学 A 再学 B"怎么来的

旧版是人工填的，既不全面也无法验证。v4 的做法：
1. **LLM 三路独立建图**：让 DeepSeek 从三个不同角度分别判断技能间先修关系——技术依赖（用 B 必须先会 A）、学习难度（A 是 B 的简化版）、社区惯例（大家通常先学 A）。三路独立是为了降低单一 prompt 的系统性偏差
2. **投票融合**：多路命中的边置信度高
3. **环检测**：去掉"A 依赖 B、B 又依赖 A"的矛盾边（断了 2 个环），保证是 DAG（有向无环图——图论术语，指没有循环依赖，这样才能排出合法学习顺序）
4. 结果：**443 条边，覆盖 93.6% 的技能**；365 次 LLM 调用，成本 2.16 元

## 7.2 路径生成算法（v4 打分选步）

拓扑排序（图论算法，保证先修课永远排前面）是硬约束；在每个"可以学了的技能集合"里按用户条件化打分选下一个：

```
pick = argmax [ 0.30 × 岗位重要性（该技能在目标岗位 JD 里的加权频率）
              + 0.25 × ZPD 匹配度
              + 0.20 × 先修紧迫度（学会它能解锁多少后续技能）
              + 0.15 × 技能趋势动量（在涨的技能优先）
              + 0.10 × 可迁移加成（与已会技能的 GraphSAGE 向量余弦相似度）
              − 0.10 × 学时惩罚（偏好短平快，控制总时长） ]
```

- **ZPD（最近发展区，Zone of Proximal Development）**：教育心理学概念——学"略难于当前水平"的内容效率最高。我们给每个技能估难度 0-1，用户水平 L 随学习推进动态更新（L ← 0.8L + 0.2×当前技能难度）。难度低于 L−0.3 的先修技能视为"显然已会"，直接跳过不排进路径——**这是个性化的主要来源：水平越高的人路径越短越聚焦**
- **可迁移折算**：会 Java 学 Go 打折——用 GraphSAGE（图神经网络，在技能关系图上学的向量）算技能相似度
- 总学时惩罚上限约 600 小时 ≈ 半年业余时间

## 7.3 效果怎么测的

【指标】Kendall's τ（肯德尔秩相关系数）：衡量两个排序的一致性。这里用来测"不同用户拿到的路径顺序差异度"——**越高说明路径越个性化**（人人相同的路径 τ≈0）。

【测量】`experiments/eval_path_v4.py`：99 个岗位 × 3 种用户水平 = 297 条路径，v3 vs v4 对比：

| 指标 | v3 旧版 | v4 新版 | 含义 |
|---|---|---|---|
| 排序个性化（order distance） | 0.001 | **0.343** | v3 几乎人人同序，v4 真正因人而异 |
| 显著性检验 | — | t=13.89, p<0.001 | 配对 t 检验（统计学术语：同一岗位两版路径配对比较），差异不是运气 |
| ZPD 违规率 | 26.5% | 17.3% | 难度跳跃过大的步骤变少了 |
| 目标技能覆盖 | 90.99% | 90.72% | 覆盖没牺牲 |
| 平均总学时 | 442h | 116h | 高水平用户不再被塞入门课 |
| 资源挂载率 | 100% | 100% | 每一步都有学习资源 |

# 第八部分 行业趋势预测

## 8.1 技能趋势面板：630 技能 × 37 个月

- 每月每技能算 **JD 份额**（该技能 JD 数 ÷ 当月总 JD 数）而不是条数——**采集量波动是乘法因子，所有技能同比例缩放，份额一除就约掉了**（答辩可能被问"为什么份额抗偏差"，就答这句）
- 样本量低于 1000 的月份不参与占比走势，避免小样本噪声被误读成趋势

## 8.2 Chronos-Bolt：模型怎么选的、怎么上岗的

【候选模型】
- **Chronos-Bolt**（亚马逊时序基础模型：在大量时序数据上预训练过的通用预测模型，我们本地 GPU 推理，实测峰值显存仅 106MB）
- **damped Holt**（阻尼指数平滑：经典统计方法，给趋势加衰减防止线性外推发疯）
- **naive**（朴素法：预测 = 最近一个月的值，是最弱基线）

【评估协议】滚动交叉验证：取尾部 24 个月，从第 12/14/16/18/20 个月分别"假装站在那个时间点"往后预测 3 个月，和真实值比 MAPE（平均绝对百分比误差：|预测−实际|÷实际）。至少 24 个非零月的技能才参评（102 个技能入选）。

【结果】

| 模型 | 中位 MAPE | 说明 |
|---|---|---|
| naive | 0.577 | 最弱基线 |
| damped Holt | 0.373 | 最强经典方法 |
| **Chronos-Bolt** | **0.307** | 比 Holt 低 17.7%，比最优基线低 14.6% |

胜率：对 Holt 73.5%，对 naive 93.1%，对最优基线 66.7%（超过 60% 的上线阈值）。

【保守上岗策略（重要设计）】**不是一刀切全换 Chronos**：逐技能比较，只有 Chronos 的交叉验证误差**严格更小**才替换（打平不换）。最终 207 个有预测的技能里 111 个用 Chronos、96 个仍用经典方法——保证任何一个技能的在线误差不回退。每个技能的预测结果里都标着 `method` 字段，用了哪个模型公开透明。

【状态机】新兴/上升/平稳/衰退四态。**新兴判定优先于数据量门槛**——否则 RAG、MCP 这类 2024 年才出现的技术永远因"历史数据不足"上不了榜，恰恰漏掉最重要的信号。

## 8.3 岗位级预测（trend_v2）

99 个岗位 × 82 个月的份额序列，naive/季节/线性/Holt/EMA 五个模型逐岗回测选模，预测未来 12 个月。**87/99 岗位标注低置信度**——岗位级月度样本稀疏，我们如实标注而不是硬给漂亮数字（这是"诚实展示"原则的一部分）。

## 8.4 公司雷达

- **国内**：42 家官网直采公司的逐日在招记录 → 7 日/30 日净增动量 → 扩张榜/降温榜
- **收缩信号双轨制（答辩要点）**：国内没有法定裁员申报制度，所以国内收缩**我们自己直测**——逐日观测"岗位集中下架 + 在招持续净减"，比任何媒体报道都快；海外用美国 WARN 裁员备案（1748 条法定申报数据）作**先行指标**，因为全球科技收缩通常从美国传导到国内。两轨在页面上分开展示、口径明确标注
- **海外参考**：25 家公司在招动量 + WARN 裁员 1748 条 + HN 招聘帖 23 个月
- **公司状态标签规则**：有裁员备案 → shrinking（收缩）；30 日净增 >0 且无裁员 → 扩张中；净增 <0 → 降温
- 公司详情页：28 天在招走势 + 动量 + 裁员记录 + 相关新闻（公司名归一化防"苹果"匹配到水果新闻）

# 第十二部分 答辩 Q&A（深度版）

**Q：词表为什么不全让大模型生成？**
A：大模型生成的词表无法验证完备性。我们的路线是"权威库打底（O*NET/ESCO）+ 真实分布校准（JD 频次阈值）+ LLM 只做审核员（910→174，淘汰率 81%）"。LLM 在它擅长的环节（判断语义）发挥作用，在不擅长的环节（保证不漏）不靠它。

**Q：86.8% 覆盖率，剩下 13% 是什么？**
A：主要是两类：描述过短的 JD（不足 200 字符不抽取）和软技能为主的岗位。注意口径是"至少抽到一个技能"，平均每条 JD 抽到 5.4 个技能。

**Q：岗位映射覆盖率只有 41.8%，是不是太低？**
A：这是精确映射的刻意选择。87,000 种职位名写法是长尾分布，精确映射覆盖头部 41.8% 的 JD 已经足够构建统计可靠的岗位画像（最低 150 JD 才成岗）。剩下 58% 硬映射只会污染画像。国内岗位走另一套规则映射，75.2% 归到具体岗位（含国聘口径，国企岗位名更多样）。

**Q：LTR 会不会过拟合教师的错误？**
A：三重保障。①教师标签本身有区分度（0-3 分分布 345/1423/543/189）；②5 折交叉验证 graded NDCG 0.937，不是背答案；③线上保留三条排序路径可切换（ltr/llm/formula），评估显示 LTR 与教师基本持平（NDCG 差 0.008）而快 30 倍零成本。教师犯的随机性错误在蒸馏中反而被"平均"掉了。

**Q：Chronos 是黑盒大模型，和你们"不迷信大模型"矛盾吗？**
A：不矛盾。我们的原则是"用评估说话"：Chronos 逐技能回测，只有严格优于经典方法才上岗（111/207），其余 96 个技能仍在用 1970 年代的 Holt 方法。每个预测都标注用了哪个模型。

**Q：你们的数据会过时吗？**
A：系统就是为这个问题设计的。国内岗位每天更新、新闻每 3 小时、全球数据每月自动跑 14 步链路。画像里技能频率带 12 个月半衰期衰减——数据越旧权重越低，系统自动"喜新厌旧"。

**Q：裁员数据是美国的（WARN），对国内用户有什么用？会不会是硬凑？**
A：首先澄清：WARN 从来不是我们唯一的收缩信号。国内没有法定裁员申报制度，所以**国内收缩是我们对 42 家公司逐日追踪直测的**——一家公司集中下架岗位、在招数持续净减，就是可计算的收缩信号，而且逐日更新，比媒体报道更快。WARN 的定位是**海外先行指标**：2022-2023 美国科技裁员潮领先国内约半年传导，它回答的是"全球风向往哪吹"，回答不了"国内哪家在裁"——后者由我们自己的逐日观测回答。两层数据在页面上分开展示、口径明确标注，不混用。国内薪资同理：官网不公开，我们明确不展示也不编造。

**Q：小程序为什么新闻不能直接跳转阅读原文？**
A：微信平台限制：个人主体小程序的 web-view 组件需要企业资质和域名备案。我们做了复制链接一键跳转。后续注册企业主体可解开。

**Q：下一步计划？**
A：①继续扩国内公司覆盖（快手/阿里等需要浏览器渲染或授权数据源）；②接入国内薪资授权数据；③校内试点收集真实用户行为日志，用真实点击数据继续训练 LTR；④申报软著。
